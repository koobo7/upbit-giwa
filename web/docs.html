01시스템 개요

INGAM은 결제 수단이 아니라 권한 계층이다. 기존 구조에서 "이 주체가 얼마까지, 어디에, 언제까지 쓸 수 있는가"를 결정하는 규칙은 카드사 서버나 애플리케이션 코드 안에 있다. INGAM은 그 규칙을 체인으로 옮긴다.

핵심 전제는 하나다. 에이전트는 금고의 키를 갖지 않는다. 에이전트가 가진 것은 자기 지갑뿐이고, 그 지갑으로 할 수 있는 일은 금고에 결제를 요청하는 것이다. 승인 여부는 전적으로 컨트랙트가 판정한다.

신뢰 경계

위임자(principal)  ── 예치·위임 발급·즉시 회수 ──▶  DelegationVault
                                                        │
에이전트(agent)    ── spend() 요청 ──────────────────▶  │ 판정
                                                        │
                     ◀── 송금 또는 커스텀 에러 ─────────┘

에이전트가 탈취되어도 컨트랙트가 정한 한도 밖으로는 나갈 수 없다. 위임자는 언제든 revoke() 한 번으로 권한을 소멸시킬 수 있고, 위임이 살아 있는 동안에도 withdraw()로 자금을 회수할 우선권을 갖는다.

02상태 모델

위임은 principal → agent 쌍 하나당 하나씩 존재하며, 단일 구조체로 관리된다.

struct Delegation {
    uint128 perTxLimit;    // 1회 결제 한도
    uint128 dailyLimit;    // 1일 누적 한도
    uint128 totalCap;      // 위임 전체 기간 총 한도
    uint128 totalSpent;    // 누적 사용액
    uint128 spentToday;    // 오늘 사용액 (dayIndex 기준)
    uint64  dayIndex;      // spentToday가 속한 날짜 (timestamp / 1 days)
    uint64  expiry;        // 만료 시각. 이후 자동 무효
    bool    active;        // 회수되면 false
    bool    whitelistOnly; // true면 허용된 수취인에게만 결제 가능
}

두 개의 허용 층

수취인과 가맹점은 별개의 층이다. 이 분리가 정산 파트너 경로에서 결정적으로 중요하다.

층키의미
allowedRecipientdelegationId → address온체인에서 실제로 자금을 받는 주소. 정산 경로에서는 파트너 주소가 된다
allowedMerchantdelegationId → bytes32쿠팡·넷플릭스처럼 체인 밖에 있는 상점의 식별자 해시
merchantPolicyOndelegationId → bool가맹점 검사 사용 여부

왜 두 층인가. 정산 파트너를 쓰면 온체인 수취인은 파트너 한 곳으로 고정된다. 수취인 화이트리스트만 있으면 "파트너에게 보내는 것"만 통제될 뿐 어느 상점에 쓰는지는 전혀 통제되지 않는다.

그래서 가맹점 단위 허용을 컨트랙트가 따로 강제한다. 해시는 keccak256(bytes(식별자))이며 merchantId()로 계산한다.

회차(nonce) 설계

위임 ID는 principal · agent · nonce로부터 파생된다. 위임을 재발급하면 delegationNonce가 증가하며 ID 자체가 바뀐다.

delegationId = _idFor(principal, agent, delegationNonce[principal][agent])

화이트리스트는 delegationId를 키로 저장되므로, 재발급 시 예전 허용 목록이 자동으로 무효화된다. 목록을 일일이 지우는 반복문이 없고, 지우다 만 상태도 존재할 수 없다.

03판정 로직

결제 경로는 spend() 하나이고, 사전 조회용으로 상태를 바꾸지 않는 canSpend()가 대칭으로 존재한다.

검사 순서

spend(principal, recipient, amount, memo)
  │
  ├─ 위임 존재?           → NoDelegation
  ├─ active?              → DelegationInactive
  ├─ expiry 이전?         → DelegationExpired(expiry, now)
  ├─ recipient ≠ 금고?    → SelfRecipient
  ├─ whitelistOnly?       → RecipientNotAllowed(recipient)
  ├─ merchantPolicyOn?    → MerchantNotAllowed(merchant)
  ├─ _applyLimits()       → PerTxLimit / DailyLimit / TotalCap
  ├─ 잔액 충분?           → InsufficientBalance(available, requested)
  │
  ├─ 상태 갱신 (Effects)
  └─ 송금 (Interactions)  → TransferFailed

한도 적용

세 한도의 성격이 다르다. 건당은 매번 초기화되고, 일일은 날짜가 바뀌면 자동 회복되며, 총 한도는 회복되지 않는다.

uint64 today = uint64(block.timestamp / 1 days);
uint128 spentToday = d.dayIndex == today ? d.spentToday : 0;

일일 사용액은 별도의 리셋 트랜잭션 없이 회복된다. dayIndex가 오늘과 다르면 spentToday를 0으로 간주하는 방식이라, 아무도 관리하지 않아도 날짜가 바뀌는 순간 한도가 돌아온다. 만료 역시 같은 원리로 아무 조치 없이 자동 무효가 된다.

커스텀 에러 — 왜 막혔는지가 돌아온다

거절 사유를 문자열이 아니라 타입과 숫자로 반환한다. 얼마가 남았는지가 함께 오므로 에이전트가 재시도 금액을 스스로 계산할 수 있다.

에러반환값의미
PerTxLimitExceededlimit, requested건당 한도 초과
DailyLimitExceededremaining, requested오늘 남은 한도 부족
TotalCapExceededremaining, requested총 한도 소진
RecipientNotAllowedrecipient화이트리스트 밖 수취인
MerchantNotAllowedmerchant허용되지 않은 가맹점
DelegationExpiredexpiry, nowTs만료됨
DelegationInactive—회수됨
SelfRecipient—금고 자신에게 송금 시도
InsufficientBalanceavailable, requested위임자 예치 잔액 부족

전체 17개 커스텀 에러가 정의돼 있다. canSpend()는 같은 판정을 거쳐 가부와 사유를 함께 반환하는 view 함수다. 대시보드는 이것으로 버튼 활성화 여부를 정하고, 정산 파트너는 승인 판단에 쓴다.

04보안 설계 결정

재진입 방어와 CEI

nonReentrant 가드를 두고, 그와 별개로 Checks-Effects-Interactions 순서를 지킨다. 한도 차감과 잔액 갱신이 모두 끝난 뒤에 외부 송금이 일어나므로, 송금 콜백이 다시 들어와도 이미 소진된 한도를 마주한다.

위임자 출금 우선권

위임이 활성 상태여도 위임자는 withdraw()로 언제든 자금을 뺄 수 있다. 위임은 지출 권한이지 자금에 대한 권리가 아니다. 에이전트가 이상 행동을 보일 때 회수를 기다릴 필요 없이 잔액 자체를 비울 수 있다.

금고 자기송금 차단

수취인을 금고 주소로 지정하면 SelfRecipient로 거절한다. 이를 허용하면 한도는 차감되는데 자금은 금고에 남아, 회수 불가능한 상태로 한도만 소각되는 경로가 생긴다.

정수 폭 선택

금액 필드는 uint128이다. 구조체가 슬롯에 조밀하게 들어가 가스가 줄고, uint256 입력은 AmountTooLarge로 경계에서 막는다. 한도 차감은 뺄셈 결과를 먼저 검사한 뒤 unchecked로 수행해 불필요한 오버플로 검사를 피한다.

EVM 버전 고정

solc 0.8.26의 기본 타깃은 cancun이고, string memory 반환에 MCOPY(0x5e)를 emit한다. 로컬 테스트에 쓰는 ganache 7.x는 이 옵코드를 구현하지 않아 canSpend()가 invalid opcode로 죽는다.

evmVersion: 'shanghai'로 고정해 로컬 테스트와 OP Stack L2에서 동일한 바이트코드가 돌도록 했다. 검증된 컨트랙트의 컴파일 설정도 이와 같다.

05정산 아키텍처

쿠팡은 ETH를 받지 않는다. 넷플릭스도, 대부분의 상점도 마찬가지다. 결제 수단을 바꾸려는 시도는 실패한다 — 가맹점을 설득하는 데 수십 년이 걸리기 때문이다.

INGAM은 결제 수단을 건드리지 않는다. 권한 계층만 체인으로 옮기고, 결제 자체는 원화로 나가도 된다.

세 가지 경로

경로대상상태
온체인 직접 정산수취인이 암호화폐를 직접 받는 경우. API 크레딧, 클라우드동작 중
정산 파트너 경유원화만 받는 곳. 쿠팡, 넷플릭스Phase 1
선불 크레딧 브리지상품권·포인트 전환. 보조 수단보류

파트너 경유 흐름

에이전트가 쿠팡에서 결제 시도
        ↓
카드 승인 요청이 정산 파트너(PG·카드사)에게 도달
        ↓
파트너가 canSpend(위임자, 에이전트, 가맹점, 금액) 조회
        ↓
  true  → 파트너가 원화로 대납. 쿠팡은 정상 결제 완료
  false → 승인 거절. 사유(PER_TX_LIMIT 등)가 그대로 반환
        ↓
파트너가 정산 주기에 맞춰 금고에서 회수

쿠팡은 아무것도 몰라도 된다. 평소처럼 카드 결제를 받을 뿐이다. 에이전트도 특별한 일을 하지 않는다. 그런데 한도는 온체인에서 강제된다.

canSpend()는 처음부터 이 용도로 설계됐다. 상태를 바꾸지 않는 view 함수라 파트너가 승인 판단에 쓰기 적합하고, 거절 사유를 함께 돌려준다. 파트너 연동에 필요한 인터페이스는 이미 배포돼 있다.

선불 크레딧 브리지는 구현이 가장 쉽지만 잔액이 체인 밖에 머무는 구간이 생겨 회수의 즉시성이 약해진다. 파트너 확보 전의 임시 수단으로만 본다.

06왜 GIWA인가

정산 파트너는 규제 대상이다. 누구에게 대납하는지 모르면 사업을 할 수 없다. 익명 지갑이 익명 지갑에 권한을 넘기는 구조는 어떤 PG도 받지 않는다.

도장(Dojang)이 이 문제를 푼다는 것이 INGAM의 핵심 주장이다. KYC 라이선스 기관이 발급한 온체인 검증이 위임의 뿌리에 있으면, 파트너는 "실명 확인된 위임자가 이 한도를 승인했다"를 체인에서 직접 확인한다. 별도 계약서도 심사도 필요 없다.

GIWA 구성 요소INGAM에서의 역할
도장(Dojang)위임 뿌리의 KYC 검증. 파트너 연동의 전제
업비트 온램프금고 충전 경로
L2 수수료 구조소액·고빈도 정산을 경제적으로 성립시킴
기와 월렛즉시 회수 버튼이 놓일 자리

네 가지가 동시에 필요하다. 하나라도 빠지면 정산 파트너 경로가 성립하지 않는다.

07테스트 전략

34개 규칙 검증이 npm test 하나로 돌아간다. 설치 없이 로컬 체인에서 전체 시나리오가 재생된다.

테스트의 중심은 "성공하는 경우"가 아니라 차단되어야 하는 경우를 각각 어떤 에러로 막는지다. 단순히 revert 여부만 보지 않고 에러 타입까지 단언한다.

08범위와 로드맵

현재 MVP는 네이티브 코인 결제만 지원한다. 이 범위를 의도적으로 좁게 잡았다 — 권한 계층이 실제로 뚫리지 않는다는 것을 먼저 증명해야 나머지가 의미를 갖기 때문이다.
